# OrynX Distributed Observability & Operational Intelligence (Step 26)

> **Cross-Reference**: This document extends [docs/OBSERVABILITY.md](./OBSERVABILITY.md) (Steps 22–23 baseline), [docs/SLO.md](./SLO.md), [docs/ALERTING.md](./ALERTING.md), and [docs/RESILIENCE_ENGINEERING.md](./RESILIENCE_ENGINEERING.md) (Step 25).

## 1. Observability Architecture

OrynX provides end-to-end distributed tracing, centralized structured log aggregation, low-cardinality operational metrics, and unified trace-to-log-to-metric investigation across all 5 backend services (`gateway-service`, `auth-service`, `orchestrator-service`, `planning-service`, `execution-service`) and the Next.js frontend.

```text
Frontend (Next.js)
  |-- HTTP (traceparent, X-Request-ID, X-Correlation-ID) --> Gateway (:8080)
  |-- STOMP WS (X-Request-ID, X-Correlation-ID) -----------> Orchestrator (:8082)
                                                               |
  Services (Java 21 / Spring Boot 3.5 + OTel Agent 2.11.0 + OTel API 1.44.1)
    |-- Kafka (W3C traceparent/tracestate + X-Correlation-ID + X-Workflow-ID + X-Execution-ID)
    |-- OTLP gRPC (:4317) Traces & Logs --> OTel Collector (memory_limiter, redact, batch)
    |                                          |-- Traces (otlp/tempo) ----> Grafana Tempo (:3200)
    |                                          |-- Logs (otlphttp/loki) ---> Grafana Loki (:3100)
    |-- Isolated :9100/metrics (172.29.22.x) --> Prometheus (:9090) ------> Alertmanager (:9093)
                                                    |
                                              Grafana (:3001 -> :3000)
                                    (Prometheus <-> Tempo <-> Loki <-> Alertmanager)
```

## 2. Trace Propagation & Kafka Trace Context

- **HTTP Propagation**: Standards-compliant W3C Trace Context (`traceparent`, `tracestate`) is generated by the frontend (`frontend/src/services/observability.ts`) or edge gateway (`CorrelationIdFilter`) and automatically propagated across Spring WebFlux, Spring MVC, and downstream HTTP clients by the OpenTelemetry Java Agent (`2.11.0`).
- **Kafka Propagation**:
  - `ObservabilityKafkaConfig` (`orchestrator-service`) and `ExecutionObservabilityKafkaConfig` (`execution-service`) automatically attach `TraceContextProducerInterceptor` and `TraceContextRecordInterceptor` to Spring Kafka producer and listener factories.
  - On send, `KafkaTraceContextPropagator` / `ExecutionKafkaTracePropagator` injects W3C `traceparent`/`tracestate` and sanitized `X-Correlation-ID`, `X-Request-ID`, `X-Workflow-ID`, `X-Execution-ID` into Kafka record headers.
  - On consume, the record interceptor extracts W3C parent context, starts a linked `CONSUMER` span (`orynx.kafka.consume.<topic>`), populates MDC, and unconditionally closes spans and clears MDC in `afterRecord` / `clearThreadState`.
- **Asynchronous Worker Continuity**:
  - `WorkflowExecutionDispatcher` captures the caller's OpenTelemetry `Context.current()` and MDC map before submitting work to `ThreadPoolTaskExecutor`, restores both inside the worker thread, starts child span `orynx.worker.execute`, and unconditionally calls `MDC.clear()` in `finally` to prevent cross-workflow thread-pool contamination.
  - `WorkflowExecutionEngine` creates bounded per-task spans (`orynx.task.execute`) recording `orynx.workflow.id`, `orynx.task.name`, `orynx.task.order`, `orynx.task.attempts`, and `orynx.task.success`.

## 3. Correlation Model

| Identifier | HTTP Header | Kafka Header | MDC Key | Span Attribute | Metric Label? |
|---|---|---|---|---|---|
| Correlation ID | `X-Correlation-ID` | `X-Correlation-ID` | `correlationId` | `orynx.correlation.id` | **NEVER** |
| Request ID | `X-Request-ID` | `X-Request-ID` | `requestId` | `orynx.request.id` | **NEVER** |
| Trace ID | `traceparent` | `traceparent` | `trace_id` | W3C Trace Context | Exemplar only |
| Span ID | `traceparent` | `traceparent` | `span_id` | W3C Trace Context | **NEVER** |
| Workflow ID | URI `/workflows/{id}` | `X-Workflow-ID` | `workflowId` | `orynx.workflow.id` | **NEVER** |
| Execution ID | N/A | `X-Execution-ID` | `executionId` | `orynx.execution.id` | **NEVER** |
| Attempt Number | N/A | N/A | `attemptNumber` | `orynx.task.attempts` | **NEVER** |
| Worker ID | N/A | N/A | `workerId` | `orynx.worker.id` | **NEVER** |

All incoming `X-Request-ID` and `X-Correlation-ID` headers are strictly validated against `^[A-Za-z0-9._:/-]{1,128}$` to prevent CRLF log forging and memory abuse.

## 4. Structured Logging & Sanitization

- All 5 services standardize `logback-spring.xml` using `LogstashEncoder` (`docker` profile) with fields: `@timestamp`, `level`, `service`, `environment`, `logger_name`, `thread_name`, `message`, `trace_id`, `span_id`, `requestId`, `correlationId`, `workflowId`, `executionId`, `attemptNumber`, `workerId`, `eventId`, `errorCategory`.
- **Dual-Layer Redaction**:
  1. Application layer: `ObservabilitySanitizer` / `ExecutionObservabilitySanitizer` redact Bearer tokens, JWTs, `password`/`secret`/`token`/`api_key` key-value pairs, URL credentials, and PEM private keys before logging or attaching error messages to spans.
  2. Collector layer: `otel-collector-config.yaml` enforces `attributes/redact_traces` (deleting `authorization`, `cookie`, `x_api_key`, `db.user`, `password`, `secret`, `token`) and `transform/redact_logs`.

## 5. Telemetry Pipeline, Storage & Resource Controls

- **OpenTelemetry Collector** (`orynx-otel-collector:0.114.0`, `384m` RAM / `0.5` CPU):
  - Receivers: OTLP gRPC (`:4317`) and HTTP (`:4318`).
  - Processors: `memory_limiter` (`256MiB` limit, `64MiB` spike), `filter/healthchecks`, `attributes/redact_traces`, `transform/redact_logs`, `batch` (`timeout: 2s`, `send_batch_size: 512`, `send_batch_max_size: 1024`).
  - Bounded `sending_queue` (`queue_size: 512`, `num_consumers: 4`) and `retry_on_failure` (`max_elapsed_time: 60s`) on both `otlp/tempo` and `otlphttp/loki`.
- **Grafana Tempo** (`grafana/tempo:2.6.1`, `512m` RAM / `1.0` CPU): Local filesystem WAL/blocks, `24h` block retention, loopback UI `127.0.0.1:3200`.
- **Grafana Loki** (`grafana/loki:3.2.1`, `384m` RAM / `0.5` CPU): TSDB v13 local filesystem storage, `24h` retention, `allow_structured_metadata: true` so only `service.name` and `deployment.environment` are indexed as stream labels while `trace_id`, `workflowId`, `executionId`, and `correlationId` are queried via structured metadata without label cardinality explosion. Loopback API `127.0.0.1:3100`.
- **Failure Isolation**: Backend services configure bounded OTLP batch processors (`OTEL_BSP_MAX_QUEUE_SIZE=2048`, `OTEL_BLRP_MAX_QUEUE_SIZE=2048`, `EXPORT_TIMEOUT=5000ms`). If `otel-collector`, `tempo`, or `loki` is unavailable, telemetry batches are dropped after timeout without blocking or failing workflow execution.

## 7. Trace → Log → Metric Investigation Flow

1. Start from an alert or dashboard panel (e.g., `OrynX Workflow Execution` or `OrynX Service Performance`).
2. Query Loki in Grafana Explore: `{service_name=~".*-service"} | workflowId="42"` (or filter by `correlationId`).
3. Click the extracted `TraceID` derived field link to open the full distributed trace in **Tempo** (Gateway → Orchestrator → Kafka → Execution Worker → Task Attempts).
4. Inside any Tempo span, click **Logs for this span** (`tracesToLogsV2`) to view correlated Loki logs, or **Metrics** (`tracesToMetrics`) to inspect service RPS and 5xx rates during the exact span window.

## 8. Sampling, Environment Variables & Production Considerations

| Variable | Default | Production Recommendation |
|---|---|---|
| `OTEL_TRACES_SAMPLER` | `parentbased_traceidratio` | `parentbased_traceidratio` or collector tail-sampling |
| `OTEL_TRACES_SAMPLER_ARG` | `1.0` | `0.05`–`0.20` depending on RPS |
| `OTEL_LOGS_EXPORTER` | `otlp` | `otlp` (or `none` if using node-level DaemonSet collector) |
| `OTEL_BSP_MAX_QUEUE_SIZE` | `2048` | `2048`–`4096` |
| `OTEL_BLRP_MAX_QUEUE_SIZE` | `2048` | `2048`–`4096` |
| `LOKI_MEM_LIMIT` / `TEMPO_MEM_LIMIT` | `384m` / `512m` | Dedicated horizontally scaled object-storage deployment |
| `NEXT_PUBLIC_GRAFANA_URL` | *(unset)* | Optional internal SRE Grafana URL for trace links |

**Local vs. Production Storage Disclaimer**: The Docker Compose Tempo and Loki configurations use local filesystem storage and single-tenant mode (`auth_enabled: false` on loopback `127.0.0.1`). For production, deploy Tempo and Loki with object storage (S3/GCS), TLS, multi-tenant authentication, and network policies.
